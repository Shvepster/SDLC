# Планировать проверки по полю `next_check_at` в базе данных

## Контекст и постановка задачи

Каждый API проверяется со своим интервалом от 1 до 60 минут, причём следующая проверка должна начаться через интервал после предыдущей с отклонением не более 10 секунд (REQ-FUNC-002). Счётчик неудач подряд и уже отправленные уведомления нельзя терять при перезапуске приложения, иначе после рестарта придёт повторное уведомление или не придёт нужное (REQ-FUNC-004). По оценке нагрузки до 2000 API, при интервале 1 минута это около 33 проверок в секунду.

Как организовать запуск проверок по расписанию?

## Драйверы решения

* Точность запуска: ±10 секунд
* Устойчивость к перезапуску: ничего не терять и не дублировать
* Простота и отсутствие лишних компонентов
* Возможность в будущем запустить несколько экземпляров приложения
* Ограничение по срокам (стоимость разработки)

## Рассмотренные варианты

* Планировщик на основе БД: поле `next_check_at` и выборка с `FOR UPDATE SKIP LOCKED`
* Quartz Scheduler
* Таймер в памяти на каждый API (`ScheduledExecutorService`)
* Брокер сообщений (RabbitMQ) с отложенными сообщениями

## Итог решения

Выбранный вариант: «Планировщик на основе БД», потому что расписание хранится там же, где данные, и переживает перезапуск, а `SKIP LOCKED` не даёт двум потокам или экземплярам взять одну и ту же проверку. Каждые 5 секунд выбираются просроченные API (`next_check_at <= now()`), для каждого `next_check_at` сдвигается на интервал от момента выборки, проверка выполняется в виртуальном потоке, а результат и обновление счётчика записываются в одной транзакции.

### Последствия

* Хорошо, потому что после перезапуска расписание, счётчики неудач и уведомления сохраняются; теряется не более одной пробы, взятой в момент остановки (расписание сдвигается при выборе API)
* Хорошо, потому что максимальное опоздание запуска ограничено шагом опроса (5 секунд) плюс временем выборки, то есть укладывается в 10 секунд
* Хорошо, потому что нет внешних компонентов, кроме БД
* Плохо, потому что запрос к БД выполняется каждые 5 секунд даже при отсутствии работы (нагрузка небольшая, нужен индекс по `next_check_at`)
* Плохо, потому что при очень большом числе API понадобится ограничение числа одновременных проверок (семафор, 500)

### Подтверждение

* Интеграционный тест: два планировщика на одной БД не берут один API дважды
* Тест остановки: приложение принудительно останавливается во время проверки, после запуска счётчик неудач и число уведомлений корректны
* Нагрузочный тест: 2000 API с интервалом 1 минута, не менее 99% проверок начинаются не позднее чем через 10 секунд после срока (REQ-PERF-002)

## Плюсы и минусы вариантов

### Планировщик на основе БД

* Хорошо, потому что состояние хранится транзакционно вместе с результатом
* Хорошо, потому что масштабируется на несколько экземпляров
* Нейтрально, потому что нужен свой небольшой код (около 100 строк)
* Плохо, потому что нагрузка на БД растёт вместе с числом API

### Quartz Scheduler

* Хорошо, потому что готовая библиотека с хранением расписания в БД
* Плохо, потому что для тысяч задач с разными интервалами настройка и таблицы Quartz сложнее собственного решения
* Плохо, потому что результат проверки и состояние API всё равно записываются отдельно, и согласованность нужно обеспечивать вручную

### Таймер в памяти на каждый API

* Хорошо, потому что самый простой вариант
* Плохо, потому что при перезапуске расписание теряется и нужно восстанавливать его из БД
* Плохо, потому что при нескольких экземплярах приложения проверки дублируются

### Брокер сообщений

* Хорошо, потому что масштабируется и отделяет проверки от остальной системы
* Плохо, потому что добавляет компонент, который нужно устанавливать и сопровождать, а проекту хватает одной БД

## Дополнительная информация

Затронутые требования SRS: REQ-FUNC-002, REQ-FUNC-003, REQ-FUNC-004, REQ-PERF-002, REQ-REL-001 (см. приложение B SDD). Представления SDD: 005-structure, 009-interaction-check, 011-algorithm-status, 015-concurrency, 018-resources. Решение стоит пересмотреть, если число API превысит 10 000 или потребуется точность запуска лучше 5 секунд. Связанные решения: ADR-0002.
