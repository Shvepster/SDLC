# Отправлять уведомления в Telegram через Bot API с long polling

## Контекст и постановка задачи

Во втором раунде обсуждения Заказчик добавил обязательное требование REQ-FUNC-011: сообщения о недоступности и восстановлении API должны приходить в Telegram, потому что команда постоянно работает в этом мессенджере и не держит открытой панель. Требуется привязка чата к учётной записи, отправка без участия пользователя и поведение при недоступности Telegram.

Ограничения: приложение разворачивается на одном сервере за обратным прокси и не имеет собственного публичного домена для webhook; бюджет и срок релиза зафиксированы; бюджетные уведомления (REQ-FUNC-008) по решению C11 в Telegram не отправляются.

Как доставлять сообщения в Telegram, не усложняя развёртывание?

## Драйверы решения

* Отсутствие публичного адреса и сертификата для входящих запросов
* Минимум новых компонентов и настроек
* Привязка чата к одной учётной записи, защита от чужой привязки
* Повторные попытки при сбое и сохранение статуса доставки (REQ-FUNC-004, REQ-REL-001)
* Срок и стоимость: около 14 часов на реализацию

## Рассмотренные варианты

* Telegram Bot API с получением команд через long polling
* Telegram Bot API с webhook и публичным HTTPS-адресом
* Только экран и электронная почта (без Telegram)
* Сторонний сервис уведомлений (например, агрегатор push-сообщений)

## Итог решения

Выбранный вариант: «Telegram Bot API с long polling».

* Приложение отправляет сообщения методом `sendMessage` по HTTPS на фиксированный адрес `api.telegram.org`; исходящих соединений достаточно, входящий порт и сертификат не нужны.
* Команды бот получает методом `getUpdates` с таймаутом 30 секунд в одном фоновом виртуальном потоке. Это упрощает развёртывание по сравнению с webhook.
* Привязка: пользователь в настройках запрашивает одноразовый код, отправляет боту `/start <код>`; код живёт 15 минут, хранится в памяти и удаляется после первого успешного использования. `chat_id` сохраняется у пользователя; частичный уникальный индекс не даёт привязать один чат к двум учётным записям.
* Отправка выполняется после коммита уведомления. При ошибке — три попытки (сразу, через 30 секунд и через 5 минут). Неотправленные уведомления со статусом `PENDING` подбирает sweeper каждые 30 секунд. Статус канала (`NOT_REQUIRED`, `PENDING`, `SENT`, `FAILED`) хранится в `notification.telegram_status` и не влияет на уведомление на экране и почту.
* Токен бота передаётся переменной окружения `TELEGRAM_BOT_TOKEN` и не попадает в репозиторий, базу и журналы.
* Бюджетные уведомления в Telegram не отправляются (C11): канал используется только для событий `API_DOWN` и `API_UP`.

### Последствия

* Хорошо, потому что сообщение приходит на телефон за секунды и не требует публичного адреса приложения
* Хорошо, потому что канал реализуется как второй адаптер `NotificationChannel` и не меняет `NotificationService` (ADR-0001, представление 016)
* Хорошо, потому что статус доставки и повторные попытки переиспользуют механизм, уже сделанный для почты
* Плохо, потому что long polling держит постоянное исходящее соединение и требует одного фонового потока на экземпляр приложения; при нескольких экземплярах нужен только один получатель `getUpdates`
* Плохо, потому что коды привязки хранятся в памяти и теряются при перезапуске: пользователь запрашивает новый код (безвредно, зафиксировано в REQ-REL-001)
* Плохо, потому что Telegram ограничивает частоту сообщений (порядка 30 в секунду суммарно), поэтому отправка идёт через очередь с ограничением 25 сообщений в секунду (представление 018)
* Нейтрально, потому что при недоступности Telegram уведомление остаётся на экране и отправляется по почте

### Подтверждение

* Тест привязки: код действует 15 минут, принимается один раз, занятый чат отклоняется
* Тест отправки: событие `API_DOWN` приводит к сообщению в привязанном чате не позднее чем через 1 минуту
* Тест отказа: при недоступном Telegram выполняются три попытки, статус становится `FAILED`, экран и почта не затрагиваются
* Тест изоляции: сообщения уходят только в чат владельца API
* Инспекция: токен бота отсутствует в репозитории, базе и журналах

## Плюсы и минусы вариантов

### Bot API с long polling

* Хорошо, потому что не нужен публичный адрес, сертификат и настройка входящих запросов
* Хорошо, потому что работает за обратным прокси и в закрытой сети с исходящим доступом
* Плохо, потому что постоянное соединение и один получатель на несколько экземпляров
* Плохо, потому что задержка получения команд зависит от таймаута long polling (до 30 секунд), но для привязки это не критично

### Webhook

* Хорошо, потому что мгновенная доставка команд и нет постоянного соединения
* Плохо, потому что нужен публичный HTTPS-адрес, домен и сертификат, а также проверка подлинности запросов
* Плохо, потому что усложняет локальную разработку и развёртывание на одном сервере

### Только экран и почта

* Хорошо, потому что ничего не нужно добавлять
* Плохо, потому что не выполняет REQ-FUNC-011 и бизнес-цель BO-1: письмо приходит позже и часто не читается вовремя

### Сторонний сервис уведомлений

* Хорошо, потому что готовые очереди и шаблоны сообщений
* Плохо, потому что ещё один внешний сервис, ключи и зависимость; для одного канала избыточно

## Дополнительная информация

Затронутые требования SRS: REQ-FUNC-011, REQ-FUNC-004, REQ-FUNC-008, REQ-SEC-004, REQ-REL-001, REQ-AVAIL-001. Представления SDD: 001-context, 003-logical, 008-interface, 009-interaction-check, 010-interaction-failures, 014-state-dynamics, 015-concurrency, 017-deployment, 018-resources, 019-ui-screens. Решение стоит пересмотреть при переходе на несколько экземпляров приложения (потребуется отдельный получатель `getUpdates` или webhook) или при появлении публичного домена. Связанные решения: ADR-0001, ADR-0003.
