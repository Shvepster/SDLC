# Кэшировать панель и журнал в памяти приложения библиотекой Caffeine

## Контекст и постановка задачи

REQ-PERF-001 требует кэшировать данные главной панели (TTL не более 15 секунд) и журнала расходов (не более 60 секунд). Кэш должен быть разделён по пользователям, сбрасываться при добавлении или удалении API, добавлении или импорте расхода и изменении бюджета, а также не задерживать появление нового результата проверки дольше 30 секунд. По итогам обсуждения с Заказчиком (22.11.2026) реализация кэша перенесена в версию 1.1, но решение принимается сейчас, чтобы дизайн версии 1.0 был готов к кэшу.

Где и как кэшировать данные?

## Драйверы решения

* Ключ кэша содержит идентификатор пользователя (изоляция, REQ-SEC-001)
* Простая и надёжная инвалидация
* Отсутствие новых компонентов для установки
* Ограничения на TTL из REQ-PERF-001

## Рассмотренные варианты

* Caffeine (кэш в памяти процесса)
* Redis
* Не использовать кэш

## Итог решения

Выбранный вариант: «Caffeine», потому что приложение работает одним процессом, кэш в памяти не требует отдельного сервера, а библиотека поддерживает TTL и принудительное удаление записей. Ключи кэшей: `dashboard:{userId}` (TTL 10 секунд) и `journal:{userId}:{период}` (TTL 60 секунд). Сервисы сами сбрасывают нужные ключи после изменения данных.

### Последствия

* Хорошо, потому что нет новых компонентов и сетевых вызовов
* Хорошо, потому что разделение по пользователям задаётся самим ключом
* Хорошо, потому что TTL панели 10 секунд даёт худшее время появления результата 20 секунд вместе с опросом (ADR-0004), то есть меньше 30 секунд
* Плохо, потому что при нескольких экземплярах приложения кэши не синхронизированы (потребуется Redis)
* Плохо, потому что после перезапуска кэш пуст, и первый запрос идёт в БД

### Подтверждение

* Тест: два одинаковых запроса панели в пределах TTL приводят к одному обращению к БД (проверка по журналу или метрике)
* Тест инвалидации: после добавления API или расхода следующий ответ содержит новые данные
* Тест изоляции: пользователь B не получает записей кэша пользователя A

## Плюсы и минусы вариантов

### Caffeine

* Хорошо, потому что простота и высокая скорость
* Нейтрально, потому что кэш виден только одному экземпляру приложения
* Плохо, потому что ручная инвалидация требует дисциплины

### Redis

* Хорошо, потому что общий кэш для нескольких экземпляров
* Плохо, потому что ещё один сервер и сетевые обращения; для одного экземпляра не нужен

### Без кэша

* Хорошо, потому что нет проблем с устаревшими данными
* Плохо, потому что противоречит REQ-PERF-001
* Нейтрально, потому что при нагрузке до 100 пользователей прямые запросы всё равно быстрые (этот вариант и используется в версии 1.0)

## Дополнительная информация

Затронутые требования SRS: REQ-PERF-001, REQ-FUNC-003, REQ-FUNC-009, REQ-SEC-001; открытый вопрос C8 закрыт: кэшируются панель и журнал, проверки и вход не кэшируются. Представления SDD: 018-resources, 008-interface. Связанные решения: ADR-0004.
