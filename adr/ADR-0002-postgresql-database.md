# Хранить данные в PostgreSQL

## Контекст и постановка задачи

ApiPulse хранит учётные записи, список проверяемых API, результаты проверок, расходы, бюджеты и уведомления (SRS, раздел 3.2). Часть правил должна гарантироваться самой базой: например, не более одного уведомления о пороге бюджета за календарный месяц (REQ-FUNC-008) и уникальность почтового адреса без учёта регистра (REQ-FUNC-010). Кроме того, планировщик проверок должен безопасно «разбирать» задачи при перезапуске и в будущем при нескольких экземплярах приложения (ADR-0003).

Какую базу данных использовать?

## Драйверы решения

* Строгие ограничения целостности (уникальные индексы, внешние ключи, точные денежные суммы)
* Возможность безопасно выбирать «просроченные» проверки без дублирования (`FOR UPDATE SKIP LOCKED`)
* Бесплатная лицензия и простая установка в контейнере
* Одинаковое поведение в разработке, тестах и «боевом» окружении

## Рассмотренные варианты

* PostgreSQL 16
* MySQL 8
* Встраиваемая база (H2 или SQLite)

## Итог решения

Выбранный вариант: «PostgreSQL 16», потому что он поддерживает частичные уникальные индексы, `INSERT … ON CONFLICT DO NOTHING`, `FOR UPDATE SKIP LOCKED` и точный тип `numeric(12,2)` для денег, а также работает в Docker. Схема создаётся миграциями Flyway.

### Последствия

* Хорошо, потому что ограничение «одно уведомление в месяц» выражается индексом, а не только кодом (защита от гонок)
* Хорошо, потому что планировщик (ADR-0003) использует блокировки строк без отдельного компонента
* Плохо, потому что для запуска нужен отдельный сервер БД (контейнер)
* Плохо, потому что интеграционным тестам нужен PostgreSQL (используется Testcontainers)

### Подтверждение

* Миграции Flyway применяются на пустую БД в CI
* Интеграционные тесты на PostgreSQL проверяют уникальные индексы и выборку просроченных проверок

## Плюсы и минусы вариантов

### PostgreSQL 16

* Хорошо, потому что богатые средства целостности и блокировок
* Хорошо, потому что бесплатная и популярная
* Нейтрально, потому что требует администрирования (резервные копии)
* Плохо, потому что тяжелее встраиваемых баз

### MySQL 8

* Хорошо, потому что тоже поддерживает `SKIP LOCKED`
* Плохо, потому что нет частичных уникальных индексов (нужны обходные приёмы для правила «одно уведомление в месяц»)

### Встраиваемая база (H2 или SQLite)

* Хорошо, потому что ничего не нужно устанавливать
* Плохо, потому что в SQLite нет нормальной параллельной записи, а H2 ведёт себя иначе, чем боевая база, и тесты могут давать ложный результат
* Плохо, потому что не подходит для сотен параллельных записей результатов проверок

## Дополнительная информация

Затронутые требования SRS: REQ-FUNC-008, REQ-FUNC-010, REQ-SEC-001, REQ-SEC-003. Представления SDD: 007-information, 015-concurrency, 017-deployment. Срок хранения результатов проверок и объёмы описаны в представлении 018-resources. Связанные решения: ADR-0003, ADR-0006.
