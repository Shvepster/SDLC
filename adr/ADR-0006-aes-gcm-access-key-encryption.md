# Шифровать ключи доступа к API в приложении алгоритмом AES-256-GCM

## Контекст и постановка задачи

Пользователь может указать ключ доступа к проверяемому API. Система обязана хранить его в зашифрованном виде, не раскрывать после сохранения и не писать в журналы (REQ-SEC-003). При этом ключ нужно расшифровывать при каждой проверке, значит, использовать необратимый хеш нельзя (в отличие от паролей). Ключ шифрования должен храниться отдельно от зашифрованных данных.

Как шифровать ключи доступа и где хранить ключ шифрования?

## Драйверы решения

* Если украдена только база данных, ключи доступа нельзя прочитать
* Обнаружение подмены данных (целостность)
* Простота: без дополнительных серверов и платных сервисов
* Возможность сменить ключ шифрования в будущем

## Рассмотренные варианты

* Шифрование в приложении AES-256-GCM, мастер-ключ в переменной окружения
* Шифрование на стороне БД (`pgcrypto`)
* Внешнее хранилище секретов (HashiCorp Vault или облачный KMS)

## Итог решения

Выбранный вариант: «AES-256-GCM в приложении, мастер-ключ из переменной окружения `APIPULSE_MASTER_KEY`», потому что режим GCM шифрует и проверяет целостность, а мастер-ключ никогда не попадает в базу данных. Для каждой записи создаётся случайный 96-битный вектор инициализации; в БД пишется `версия_ключа | вектор | шифротекст | тег`. В интерфейсе показывается только признак «ключ задан» и маска.

### Последствия

* Хорошо, потому что утечка дампа БД не раскрывает ключи доступа
* Хорошо, потому что поле «версия ключа» позволяет сменить мастер-ключ с перешифровкой
* Хорошо, потому что не нужны внешние сервисы
* Плохо, потому что компрометация сервера приложения раскрывает и мастер-ключ, и данные (риск принят для учебного проекта)
* Плохо, потому что потеря мастер-ключа делает все сохранённые ключи нечитаемыми (нужна резервная копия ключа отдельно от БД)

### Подтверждение

* Модульные тесты `AesKeyCipher`: шифрование и расшифровка, разные векторы для одного ключа, ошибка при изменении шифротекста
* Проверка БД: поле `access_key_enc` не содержит открытого ключа
* Проверка журналов и ответов API: ключ не встречается (REQ-SEC-003)

## Плюсы и минусы вариантов

### AES-256-GCM в приложении

* Хорошо, потому что стандартная криптография из JDK без внешних библиотек
* Хорошо, потому что ключ отделён от БД
* Нейтрально, потому что хранение мастер-ключа остаётся на совести окружения
* Плохо, потому что нужен аккуратный код (уникальный вектор, проверка тега)

### Шифрование в БД (pgcrypto)

* Хорошо, потому что меньше кода
* Плохо, потому что ключ передаётся в SQL-запросах и может попасть в журналы СУБД
* Плохо, потому что ключ и данные находятся на одном сервере БД

### Внешнее хранилище секретов (Vault или KMS)

* Хорошо, потому что лучшая защита и отзыв ключей
* Плохо, потому что отдельный компонент, который нужно установить и поддерживать; для проекта это избыточно

## Дополнительная информация

Затронутые требования SRS: REQ-FUNC-001, REQ-SEC-003, REQ-SEC-001; открытый вопрос C1: ключ передаётся в HTTP-заголовке, имя которого вводит пользователь. Представления SDD: 007-information, 008-interface, 017-deployment. Связанные решения: ADR-0002.
